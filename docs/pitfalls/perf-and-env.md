# 踩坑:性能瓶颈与环境配置

> 这一章记三类"代码没错、但跑起来不对"的问题:耗时到底花在哪、工具链版本、
> 以及多个项目共用一台机器时的端口冲突。

## 坑 1:一轮对话 54 秒,瓶颈是精排的 24 秒(不是 LLM)

**现象**:一次问答端到端 53.8 秒(710 个 token 的回答)。

**排查**:先量了各段,再直接对精排服务压测:

```
10 篇候选的单次 BGE 精排:  24.3s / 23.4s / 23.5s
```

`BAAI/bge-reranker-v2-m3`(568M 参数的 cross-encoder)在 **CPU** 上跑 10 对 (query, doc),
就是这个量级。它**吃掉了单轮耗时的一半**——而这一层当初的设计意图只是"把 10 条粗排结果
重新排个序"。

**修法**(尚未实施,按见效速度排序):
1. 候选数从 10 降到 5(直接砍半);
2. 换更小的模型(`bge-reranker-base`);
3. 上 GPU / MPS;
4. 复用已有的 `rag_cache`(同问句已能命中,但换一种问法就会重新精排)。

**原理**:两个可复用的判断。
① **耗时最长的环节往往不是直觉上最贵的那个。** 这里 LLM 生成只占一小部分,
   真正的瓶颈是一个"辅助排序"模块。不量就会一直去优化 prompt。
② 判断瓶颈的方法很便宜:**直接对那个组件压测**,而不是读代码猜。
   24.3 / 23.4 / 23.5 三个几乎一样的数,说明这是稳定的固定开销,不是偶发慢查询。

## 坑 2:Node 14 下的 npm 不认识 workspaces,`npm run` 递归派生了 301 个进程

**现象**:执行 `npm run build:client` 后,机器上出现了**几百个**不断自我派生的进程:

```
sh -c npm run build:server && npm run build:client "server"
```

一秒新增 1~2 个,清理时已经有 **301 个**。

**根因**:默认 PATH 上的 Node 是 **v14.20.0**,自带 **npm 6**——**npm 6 不支持 workspaces**。
于是 `npm run build -w client` 里的 `-w client` 没被当成 workspace 参数,
退化成"在根目录跑 `build`";而根的 `build` 脚本内容正是:

```json
"build": "npm run build:server && npm run build:client"
```

`build:client` 又是 `npm run build -w client` → 回到根 `build` → 无限递归。

而项目 `.nvmrc` 写的是 **20**,机器上也装了 v20.20.2,只是没切过去。

**修法**:切到 Node 20(`nvm use`),`npm run` 一切正常。

**原理**:`.nvmrc` 这种文件**不会自动生效**——它是给 `nvm use` 读的,不切过去等于没写。
表现又是一个典型的"症状离根因很远":报错信息里没有任何"Node 版本不对"的提示,
只有几百个看起来一样的 shell 进程。

> 遇到"同一条命令反复自我派生的进程"这类怪象,先查**工具链版本**,
> 尤其当项目里有 `.nvmrc` / `.python-version` 这类声明文件时。

## 坑 3:两个项目共用一台机器,后端端口撞车,前端静默连到别人家

**现象**:baby-ai 的前端跑起来后聊天不工作——它把请求打到了**另一个项目**的后端上。

**根因**:`client/vite.config.ts` 的代理默认目标是 `http://localhost:8002`,
而 **8002 这时被 EvalFlow(评测平台)的后端占着**;baby-ai 自己的 python-server 实际跑在 **3001**。

两个服务都是 FastAPI,接口前缀也相近,所以不会立刻报 CORS 或 404,
而是"能连上、但返回的是别人家的响应"。

**修法**:vite 配置里本来就留了开关,启动时覆盖即可:

```bash
BACKEND_URL=http://localhost:3001 npx vite
```

(注意:**默认值仍然指向 8002**,裸跑 `npx vite` 会踩雷。)

> **2026-10-16 更新 —— 这条坑又发生了一次,而且这次说明"记下来"不够。**
>
> 这次的形态和上次几乎一样:baby-ai 的后端没起,8002 上坐着 evalflow,
> 前端静默连过去、点「来一题」返回 404。**排查路径和上次一模一样** ——
> 也就是说,把结论写进文档并没能阻止它复发,因为文档靠人记得来看。
>
> 改成了四件**可执行**的事(细节见 `client/vite.config.ts` 与 `scripts/devguard.mjs`):
>
> 1. **端口固定且各项目不重叠**:baby-ai 前端 `5180` / 后端 `8010`;
>    evalflow 前端 `5173` / 后端 `8002`(让不开 8000 —— 那是 docker 里的 Chroma)。
> 2. **Vite 开 `strictPort`**:端口被占直接报错退出,不再默默顺延到 5174、5175。
>    顺延是"我打开 localhost:5173 看到的却是别的项目"的来源。
> 3. **后端 `/api/health` 返回 `service` 字段自报身份**:
>    光看 `{"status": "ok"}` 无法判断对面是谁,任何一个 FastAPI 服务(包括 Chroma)都会这么答。
> 4. **`npm run dev` 开头跑 `scripts/devguard.mjs`**:启动前就问一遍"对面是谁",
>    不是本项目就拦住并说清症状与病因的对应关系。
>
> 原理那一段没变,变的是**它现在由脚本保证,而不是由记性保证**。

**原理**:多个项目并存时,**"端口撞车"是最难查的一类问题**,因为网络层一切正常。
两个可复用的习惯:
① 每个项目用**固定的、非默认的端口**,并写进 README;
② 起服务后**先验证你连的是谁**(比如打一下只有本项目才有的接口),别等业务出错才发现。
