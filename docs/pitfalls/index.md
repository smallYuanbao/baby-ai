## 几条反复出现的底层规律

1. **失败要显式,不能静默。** 这批坑里最耗时的几个都不是"报错",而是"不报错但结果是错的":
   空回答被当成正常回答、取不到的字段渲染成空白、算错的分数显示成 100%。
   判断标准:**这次失败,有没有任何一处会让我知道?** 没有的话,先加可观测性再修 bug。
   (预算坑 2 的定位速度,完全靠新加的一条日志把 `finish_reason=length` 打了出来。)

2. **改一个被多处共用的值,验证必须覆盖每一条调用链。** 那个把 `1000` 换成常量的提交
   顺手改错了变量,而它的验证只覆盖了非流式路径——**"52 测试全绿"和"流式全挂"同时成立**。

3. **同步代码写在 `async def` 里,阻塞的是整个进程,不是那个请求。**
   判断方法只有一个:这个函数里有 `await` 吗?

4. **量,别猜。** 瓶颈在精排不在 LLM、预算峰值来自"意图模糊"而非"问题长"、
   空响应不会累积打开熔断——三条结论都和直觉相反,全是实测出来的。

5. **工具链版本是隐性依赖。** `.nvmrc` 不会自动生效;换模型会让既有参数的**语义**改变,
   而代码不会因此报错。
